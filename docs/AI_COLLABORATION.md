# AI_COLLABORATION

이 프로젝트는 Anthropic의 Claude(Claude Code)와 함께 진행했다.
**과장하지 않는 것이 이 문서의 목적이다.** 내가 직접 구현하지 않은 부분은 그렇게 적었다.

아래에서 "나"는 저자, "Claude"는 AI를 뜻한다.

---

## 1. 작업 구조

```
나      문제 정의 · 성공 기준 · 지표 정책 · 각 단계의 판단 · 서버 실행
         │
         ▼
Claude  설계 제안 · 스크립트와 러너 작성 · 로컬 점검(합성 데이터)
         │
         ▼
나      서버에 올려 SLURM 제출 → 로그와 결과 파일을 대화로 가져옴
         │
         ▼
함께     결과 해석 · 다음 단계 결정 · 기록 갱신
```

**Claude는 서버에 접근하지 않았다.** 제출·모니터링·결과 회수는 전부 내가 했다.
Claude가 결과를 본 것은 내가 가져온 로그와 파일을 통해서다.
이 구조 때문에 **AI가 자기 코드의 실행 결과를 직접 확인할 수 없었고**, 검증은 내 쪽에서 일어났다.

## 2. 내가 정한 것

| 결정 | 내용 | 영향 |
|---|---|---|
| **문제 정의** | 정답 없이 후보 100개 중 5개를 고르는 문제로 설정 | 프로젝트 전체 |
| **성공 기준** | Top-5 안에 정답 근접 후보가 하나 이상. 제출 형식이 5개이기 때문 | 평가 명세 |
| **지표 정책** | k=1/3/5를 동시에 보고하고 상황에 따라 판단 | 31번 이후 전부 |
| **조합의 범위** | "조합이 꼭 쌍일 필요는 없다. 3~5개짜리도 조합이다" | **결정적.** 33번이 쌍 전수 탐색에서 beam search로 바뀌었다 |
| **33번의 역할 정의** | 단독으로는 무의미하나 묶으면 유의미해지는 조합 찾기. 3개 이상 포함. 10세트 이상이면 영향력 순위 | 33번 명세 그대로 |
| **합집합 검토 요구** | "왜 조합을 1세트만 쓰는가. 왜 하필 4개짜리인가" | 34번 전체가 이 질문에서 나왔다 |
| **통제 비교 요구** | 집합만 다르고 나머지는 전부 같게 | 35번의 고정 조건 9항 |
| **정지 사건의 대응 순서** | 코드를 고치기 전에 데이터를 먼저 확인한다 | §4 참조 |
| **다음 사이클 진입 방식** | 구현이 아니라 설계 논의부터 시작하도록 지시 | 38번 |
| **감시 역할 요구** | "전긍정이면 안 된다. 내 생각이 최종 목표에 더 맞는지 항상 확인해 달라" | Claude가 여러 차례 내 제안에 반대 의견을 냈다 |
| **포트폴리오 주지표** | dev OOF만 주지표로 쓴다 | README |

**최종 feature를 7개로 줄인 것은 Claude의 제안이다.** 나는 7개를 전제로 후속 작업을 진행했고
37번 제작에 동의했다. 다만 "7개로 하자"는 명시적 승인 문장은 기록에 없다(`확인 필요`).

## 3. Claude가 한 것

| 항목 | 비고 |
|---|---|
| **28~38번 스크립트와 러너 작성** | 본체와 SLURM 러너. **내가 직접 작성하지 않았다** |
| **규칙 A (생성기 다양성 선택)** | 제안·구현 모두 Claude. 성능에 가장 크게 기여한 단일 장치 |
| **비대칭 등급 경계** | 평가가 2Å 이진이므로 성공 경계 근처만 벌리는 설계 |
| **그룹 = 타깃 랭킹 전환** | 전역 AUC 함정을 진단하고 교체 제안 |
| **공헌도 분해 의무화** | 선택 규칙 몫과 모델 몫을 나누는 대조군 설계 |
| **사전 등록 관행** | 35~38번이 실행 전에 문턱을 코드 상수로 박고 보고서에 찍는 구조 |
| **선택 편향 정량화** | 탐색 수에 따른 기대 최댓값 보정, 섞기 기준선 |
| **판정 통계 교정** | 36번 부호 검사의 거짓 양성을 모의 3,000회로 확인하고 분산분석으로 교체 |
| **순증 판정** | 38번. "구조한 수"만 보던 결함을 합성 점검으로 잡아 교체 |
| **자체 검증 4종** | 37번. 저장-재적재 / 앞 단계 재현 / feature 순서 가드 / 독립 스크립트 대조 |
| **디버깅 보조** | 정지 사건에서 가설 수립, 조회 스크립트(99번) 작성, 스택 덤프 해석 |

**01~27번(Process A)의 작성 주체는 이 레포의 근거 기록에 명시돼 있지 않다 — `확인 필요`.**
HANDOFF 문서가 작성 주체를 명시한 것은 28~38번뿐이다. 추측해서 적지 않았다.

## 4. AI 출력을 어떻게 검증했나 — 실제 사례

### 사례 1. 샤드 정지 — 제안받은 패치를 적용하지 않고 데이터를 먼저 봤다

**상황.** Process A 전체 확대에서 샤드 6개가 23시간 30분 동안 멈췄다. 상태는 계속 RUNNING이었다.

**Claude의 첫 제안.** "대칭이 심한 입력에서 조합이 폭발한다"는 가설과, 그에 맞춘
후보별 타임아웃(180초 초과 시 강제 종료) 구현. 문법·제어흐름 검증까지 마친 패치였다.

**내 판단.** **적용하지 않고 보류했다.** 가설이 맞는지 데이터로 먼저 확인하기로 했다.
근거 없이 타임아웃을 걸면 멀쩡한 데이터를 버린다.

**검증 과정.** 조회 전용 스크립트를 돌려 가설을 하나씩 확인했다.

| 가설 | 확인한 것 | 결과 |
|---|---|---|
| 입력 대칭성 | 전체 4,603개의 원자 수·대칭 비율 분포 | 기각. 멈춘 구간의 입력이 평범한 범위 |
| 입력 크기 | 멈춘 샤드 vs 정상 샤드 파일 크기 분포 | 기각. 두 집단이 사실상 동일 |
| 일시적 환경 장애 | 같은 샤드를 이틀 뒤 재실행 | 기각. 같은 지점에서 재현 |

**결정적 단계 — 프로세스를 직접 봤다.** 가설 셋이 다 기각된 뒤에도 원인을 몰랐다.
작업 노드에 접속해 실행 중인 프로세스 상태를 직접 조회했다.

- CPU 97.4%, 열린 입력 파일 없음 → **I/O 대기가 아니라 연산 무한루프**
- 스택 덤프로 멈춘 함수와 호출 경로, 그리고 **정확히 어느 후보인지**까지 특정
- 리소스 집계 도구(`sstat`)의 CPU 시간은 자리표시자 값을 반환해 쓸 수 없었다.
  프로세스 상태를 직접 본 것이 결정적이었다

**원인.** 후보 하나의 예측 기하가 붕괴해, 좌표 기반 연결성 추론이 결합 42개 대신 398개를 만들었다.
원자 38개에 결합 398개는 화학적으로 불가능하다. 그 과밀 그래프에서 동형 탐색이 끝나지 않았다.

**결과.** 타임아웃 대신 **원인에 맞는 검사**를 넣었다(추론 결합 수가 템플릿의 2배를 넘으면 매칭 미시도).
수 밀리초에 걸러지고, 사유가 구체적으로 남고, 후보를 통째로 버리지 않는다.
**보류한 판단이 옳았다.** 타임아웃을 적용했다면 틀린 기준으로 데이터를 버렸을 것이다.

### 사례 2. 보고서 표기 — 숫자가 무엇을 재는지 확인

37번 첫 판 보고서에서 dev 열이 **학습 데이터를 다시 예측한 in-sample 값**인데 표시가 없었다.
홀드아웃 값 옆에 나란히 있어 성능으로 읽혔다. 지적 후 열 이름을 바꾸고 out-of-fold 값과
암기 격차를 함께 싣도록 재실행했다.

### 사례 3. 결과 재현을 스크립트 안에 넣게 했다

뒤 번호 스크립트가 앞 번호의 수치를 다시 계산해 일치하는지 확인하고, 불일치면
`STATUS=CHECK_REQUIRED`와 종료 코드 2로 멈추게 했다. 31번이 30번 수치를 소수 4자리까지 재현했고,
37번이 35번 수치를 재현했다. **AI가 쓴 코드를 사람이 전부 읽어 검증할 수는 없으므로,
코드가 스스로 앞 단계와 대조하게 만든 것이다.**

### 사례 4. 사전 등록으로 사후 합리화를 막았다

판정 문턱과 "무엇을 고르지 않을지"를 실행 전에 코드 상수로 박고 보고서에 찍게 했다.
실제로 38번에서 사전 등록한 문턱 하나가 **무작위도 통과하는 무의미한 조건**으로 드러났는데,
함께 계산해 둔 무작위 기준선이 그것을 잡았다. 문턱은 지우지 않고 무효라고 적은 채 남겼다.

## 5. Claude가 틀렸고 바로잡은 것

| # | 오류 | 어떻게 드러났나 |
|---|---|---|
| 1 | 잡음 기준으로 설정 하나의 분산을 썼는데 그것이 최소분산 설정이었다 | 통합 RMS로 재검증. 같은 결론을 얻었고 미리 둔 하한이 우연히 보호했다 |
| 2 | 패치의 `\n`이 셸 계층에서 줄바꿈으로 바뀌어 문자열 3곳이 깨졌다 | 이후 패치에서 이스케이프 금지 규칙 채택 |
| 3 | "조합으로 개선했다"고 판단 | dev 이득이 선택 편향 범위 안이었다. 홀드아웃에서 소멸 |
| 4 | "집합 선택은 영향이 없다"고 예측 | 전체로는 영향이 있었다. 고정 축 층에서만 예측대로 |
| 5 | 보고서에 in-sample 값을 표시 없이 홀드아웃 옆에 배치 | 사례 2 |
| 6 | 진단 문턱이 무작위도 통과하는 조건이었다 | 사례 4 |
| 7 | 다양성 규칙을 "구조한 수"로만 판정하게 작성 | 실행 전 합성 점검에서 발견. 순증으로 교체 |
| 8 | 다음 작업으로 새 feature 추출을 1순위로 권고 | 진단 결과가 선택 쪽을 가리켰다. 더 싸고 확실한 쪽으로 순서 교체 |
| 9 | 첫 가설(입력 대칭성)에 맞춘 타임아웃 패치 | 사례 1. 데이터로 기각 |

## 6. 이 방식에 대한 평가

**잘 맞은 것**

- 학습이 분 단위로 끝나는 단계에서, 절제 실험과 대조군을 "비용이 싸니까 다 돌리자"로 밀어붙인 것.
  사람 혼자면 구현 부담 때문에 생략했을 비교들이다.
- 사전 등록·자체 검증·공헌도 분해처럼 **스스로를 의심하는 장치**를 코드에 넣은 것.
  AI가 쓴 코드를 전부 읽어 검증할 수 없다는 제약에 대한 현실적인 대응이었다.

**한계**

- Claude는 서버 실행 결과를 직접 볼 수 없었다. 내가 로그를 옮기는 과정에서 무엇을 보여줄지 내가 골랐다.
- 정지 사건에서 보듯, AI의 가설은 그럴듯하지만 틀릴 수 있고 **그에 맞춘 패치도 함께 그럴듯하다.**
  실행 중인 프로세스를 직접 보기 전까지는 좁혀지지 않았다.
- 01~27번의 작성 주체가 기록에 없다는 사실 자체가 기록 관리의 공백이다.

## 7. 이 레포에 대하여

수치는 전부 `results/`의 파일이나 원본 기록에서 읽은 값이고, 출처는 각 문서에 적었다.
