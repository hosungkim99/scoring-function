# LESSONS

이 프로젝트에서 실제로 틀렸거나 틀릴 뻔했던 지점에서 얻은 것이다.
도메인과 무관하게 **그룹 안에서 상위 k개를 고르는 문제** 전반에 적용된다.

각 항목은 **교훈 / 어떻게 드러났나 / 무엇을 바꿨나** 순서다.

---

## 1. 평균 지표는 상위 집중 지표를 대체할 수 없다

**교훈.** 평가가 "상위 k개 안에 정답이 있는가"라면, 진단 지표도 상위 가중이어야 한다.
전체를 평균하는 지표는 상위 몇 개의 품질에 거의 반응하지 않는다.

**어떻게 드러났나.** 같은 종류의 실수를 **두 번** 했다.

| 지표 | 언제 | 문제 |
|---|---|---|
| 전역 AUC | 28번 | 그룹을 가로지르는 쌍까지 센다. 그룹 난이도만 맞혀도 오른다 |
| 그룹별 AUC | 29번 | 그룹 안으로 좁혔지만 순위 **전체**를 평균한다. 우리는 상위 5개만 본다 |

전역 AUC 0.8022와 Top-5 lift −0.0134가 동시에 나왔을 때, 지표가 과제를 재지 않고 있었다.

**무엇을 바꿨나.** 주지표를 난이도 층별 lift로 바꾸고, NDCG@5·hit@k를 보조로 썼다.
그룹 안에서 상수인 feature가 중요도 상위에 올라오면 전역 지표 함정의 신호로 본다.

---

## 2. 지표의 여백을 먼저 확인한다 — 포화된 지표로는 아무것도 못 잰다

**교훈.** 지표의 개선 여지가 모델의 기대 효과보다 작으면, 그 지표는 개발 지표가 될 수 없다.
**실패가 반복되면 목표를 바꾸기 전에 측정을 의심한다.**

**어떻게 드러났나.** 모델을 다섯 번 고쳤고 다섯 번 다 "무작위보다 나쁨"이 나왔다.
목표 구조를 바꾸려다 그 전에 지표를 점검했다. Top-5는 무작위가 **0.9133**으로 포화돼 있었다.
같은 점수 파일을 Top-1(무작위 0.7406)로 **재채점만** 하자 다섯 실행이 전부 양수였다.
모델은 처음부터 작동하고 있었다.

같은 성질이 feature 개수에서도 나타났다. 중요도 상위 5개와 57개가 시드 간 잡음 범위 안에서 같다.
"47개가 기여하지 않는다"가 아니라 **"이 지표로는 구분되지 않는다"**가 정확한 서술이다.

**무엇을 바꿨나.** Top-5는 수용 기준으로만 두고 Top-1을 주 품질 지표로 삼았다.
새 지표를 쓸 때는 무작위 기준선과 상한을 먼저 계산해 여백을 적는다.

---

## 3. 선택 규칙도 모델의 일부다

**교훈.** "점수 상위 k개를 고른다"는 자명해 보여서 코드에 박아 두기 쉽다.
그런데 그것이 모델 기여의 **부호**를 바꿀 수 있다.

**어떻게 드러났나.** 모델의 1등은 무작위보다 좋은데 모델이 고른 5개 묶음은 무작위 5개보다 나빴다.
설명은 하나뿐이다 — 상위 5개가 서로 닮아 함께 틀린다. 무작위 5개는 독립 추출이라 동시에 틀릴 확률이 낮다.

**같은 점수 파일, 재학습 없이** 선택 방식만 바꾼 결과:

| | Top-5 성공률 |
|---|---|
| 점수 상위 5개 | 0.9058 (무작위 0.9133보다 낮음) |
| 규칙 A (생성기별 1위 먼저) | **0.9347** |

**무엇을 바꿨나.** 선택 규칙을 평가 코드에 내장하고, 실행마다 규칙 3종을 함께 보고한다.
평가 파이프라인에서 암묵적으로 고정된 것이 무엇인지 적어 둔다.

---

## 4. 새 구성요소는 "그것만 넣고 모델은 뺀" 대조군과 함께 잰다

**교훈.** 분해하지 않으면 데이터 구조가 주는 이득을 모델 공로로 기록한다.

**어떻게 드러났나.** 규칙 A는 층화 추출이라 **모델 없이도** 무작위보다 낫다.
점수 없는 대조군(의사난수 순서)을 같이 돌려 보니 k=5 기준 다양성 몫 **+0.0128**, 모델 몫 **+0.0101**로
대략 반반이었다. 분해하지 않았다면 +0.0229 전부를 모델 성과로 적었을 것이다.

**무엇을 바꿨나.** 공헌도 분해를 의무화했다. 대조군 = 같은 선택 규칙 + 점수 없는 결정적 순서.

---

## 5. 개입은 순증으로 판정한다 — "구조한 수"만 보면 속는다

**교훈.** 어떤 개입이 실패를 몇 개 구했는지만 세면 안 된다.
**원래 맞히던 것을 몇 개 잃었는지** 함께 세야 한다.

**어떻게 드러났나.** 다양성을 더 강제하는 축을 시험했다. 실패 그룹 26개를 구했다.
그러나 같은 규칙이 원래 맞히던 **77개를 잃어** 순증이 −51이었다. 다양성을 강제하면 뒷자리가
점수 낮은 영역으로 밀리기 때문이다. 이 결함은 실행 전 **합성 데이터 점검**에서 발견했다.

**무엇을 바꿨나.** 판정식을 `순증 = 구조(실패→성공) − 손실(성공→실패)`로 바꾸고 문턱을 사전에 정했다.

---

## 6. 조용한 실패 — 중간 단계가 엉터리 결과를 정상처럼 넘긴다

**교훈.** 실패를 실패라고 알리지 않는 단계가 있으면, 다음 단계가 무한히 돌 수 있다.
각 단계의 출력이 **상식적 범위인지** 검사해야 한다.

**어떻게 드러났나.** 샤드 6개가 23시간 동안 멈췄다. 원인은 후보 하나였다.

- 구조 파일에 결합표가 없어 좌표 거리로 연결성을 추론해야 했다.
- 그 후보는 예측 기하가 붕괴해 원자들이 비정상적으로 밀집해 있었다.
- 추론이 결합 42개 대신 **398개**를 만들었다. 원자 38개에 결합 398개 = 평균 차수 20.9로, 화학적으로 불가능하다.
- 그 과밀 그래프에서 정상 템플릿을 찾는 부분구조 동형 탐색은 경우의 수가 끝나지 않는다.

**방어 장치가 이미 셋 있었는데 하나도 걸리지 않았다.** 원자 수는 정확히 맞았고(38),
추론 함수는 예외 없이 "성공"을 반환했으며, 매칭 결과가 없는 것도 아니었다.
다만 내용물이 엉터리였을 뿐이다. **"버려야 할 것을 붙잡은" 게 아니라 "버려야 할 것인지 알아볼 눈이 없었다."**

**무엇을 바꿨나.** 출력의 타당성 검사를 넣었다 — 추론 결합 수가 템플릿의 2배를 넘으면 기하 붕괴로 보고
매칭을 시도하지 않는다. 사유도 `degenerate_inferred_connectivity`로 구체적으로 남긴다.
이 검사에 걸린 것은 175개(0.038%)뿐인데, **그 175개가 샤드 6개(27,600 후보)를 막고 있었다.**

## 7. 코드를 고치기 전에 데이터를 확인한다

**교훈.** 원인을 모르는 상태에서 넣는 방어 코드는 근거 없는 기준으로 멀쩡한 데이터를 버린다.

**어떻게 드러났나.** 위 정지 사건에서 첫 가설은 "대칭이 심한 입력 때문에 조합이 폭발한다"였다.
그 가설에 맞춰 후보별 타임아웃(180초 초과 시 강제 종료)을 구현하고 문법·제어흐름 검증까지 마쳤다.
**그런데 서버 적용은 보류하고 데이터부터 확인했다.**

가설 셋이 모두 데이터로 기각됐다.

| 가설 | 확인한 것 | 결과 |
|---|---|---|
| 입력 대칭성 | 전체 4,603개의 원자 수·대칭 비율 분포 | 멈춘 구간의 입력이 평범한 범위. 가장 대칭이 심한 입력은 멈춘 샤드에 있지도 않음 |
| 입력 크기 | 멈춘 샤드 vs 정상 샤드의 파일 크기 분포 | 두 집단이 사실상 동일. 가장 큰 파일들은 정상 완료된 샤드에 있음 |
| 일시적 환경 장애 | 같은 샤드를 이틀 뒤 재실행 | **같은 지점에서 재현.** 우연한 장애가 아님 |

**보류한 판단이 옳았다.** 타임아웃을 적용했다면 틀린 기준으로 데이터를 버리고,
180초를 낭비한 뒤 건너뛰며, 로그에는 원인이 "timeout"으로만 남았을 것이다.

**무엇을 바꿨나.** 원인을 확정한 뒤 **원인에 맞는** 검사를 넣었다(교훈 6).
타임아웃 구현은 되돌렸다.

## 8. 추정으로 좁혀지지 않으면 실행 중인 프로세스를 직접 본다

**교훈.** 멈춘 작업을 죽이기 전에 상태를 확인한다.

**어떻게 드러났나.** 가설을 셋 세우고 셋 다 기각된 뒤에도 원인을 몰랐다.
실행 중인 프로세스를 직접 조회해서야 확정됐다.

- CPU 97.4%, 열린 입력 파일 없음 → **I/O 대기가 아니라 연산 무한루프**
- 스택 덤프 → 멈춘 함수와 그 호출 경로, 그리고 정확히 어느 후보인지까지 특정
- 참고: 리소스 집계 도구(`sstat`)의 CPU 시간은 자리표시자 값을 반환해 판별에 쓸 수 없었다.
  **프로세스 상태를 직접 본 것이 결정적이었다.**

---

## 9. 잡음은 추정하지 말고 측정하되, 대표값을 잘 고른다

**교훈.** 판정의 분모가 되는 잡음은 시드를 바꿔 직접 재야 한다. 그리고 **어느 설정의 분산을 쓰는지**가 중요하다.

**어떻게 드러났나.** 시드 5회 반복으로 흔들림을 측정했다. 그런데 허용 오차의 기준으로 설정 하나의
표준편차를 썼는데, **하필 그것이 분산이 가장 작은 설정**이었다. 문턱이 실제보다 좁았다.
여러 설정을 통합한 RMS로 재검증해 같은 결론을 얻었고, 미리 둔 하한이 우연히 보호했다.

**무엇을 바꿨나.** 잡음 대표값을 설정 하나가 아니라 통합값으로 잡는다. 하한도 함께 둔다.

---

## 10. 많이 고를수록 홀드아웃에서 많이 떨어진다

**교훈.** 탐색 횟수 자체가 성능을 부풀린다. **골라내기는 되지만 미세조정은 안 된다.**

**어떻게 드러났나.** 조합 1,294개를 탐색해 dev에서 +0.0069를 더하는 feature 4개를 찾았다.
홀드아웃에서 그 기여가 −0.0056으로 사라졌다. 더 분명한 신호는 이것이다.

- 탐색을 많이 거친 집합일수록 홀드아웃에서 더 많이 떨어졌다(0.030 vs 0.017).
- **dev 1위가 홀드아웃 1위인 경우가 9칸 중 0칸.** dev 성적으로 집합을 고르는 데 정보가 없었다.
- 반면 "쓸모없는 feature만 뽑으면 망한다"는 분명하게 확인됐다. 선별 자체는 효과가 있다.

**무엇을 바꿨나.** 최고 후보와의 차이가 측정 잡음의 2배를 넘지 않으면 더 단순한 쪽을 남긴다.
탐색 수에 따른 기대 최댓값을 보정해 "실력인지 운인지" 판정한다.

---

## 11. 판정 규칙은 실행 전에 코드에 박는다 — 틀려도 지우지 않는다

**교훈.** 결과를 본 뒤 문턱을 바꾸면 무엇이든 증명할 수 있다.

**어떻게 드러났나.** 진단 문턱으로 "정답의 최고 순위 중앙값이 3 이하면 선택 문제"를 사전에 정했다.
**그런데 섞은 순서(무작위)의 중앙값도 1이었다.** 쉬운 그룹이 87%라 중앙값이 포화된 것이다.
문턱이 아무것도 구분하지 못했다.

이것을 잡아낸 것은 **함께 계산해 둔 무작위 기준선**이었다.

**무엇을 바꿨나.** 진단 지표에도 무작위 기준선을 항상 함께 계산한다.
사전 등록한 문턱은 무효임을 적은 채 **지우지 않고 남겼다.**

---

## 12. 결측은 0이 아니다

**교훈.** 계산할 수 없는 값을 0으로 채우면 "값이 0이다"라는 틀린 신호가 된다.

**어떻게 드러났나.** 결합 에너지가 0이면 "결합하지 않음"으로 읽힌다. 실제로는 "계산 못 함"이다.
null로 두고 트리 모델이 결측을 분기 한쪽으로 보내는 방향을 학습하게 했다.
추론 스크립트에도 같은 경고를 넣었다 — **빈 값으로 두어야 하고, 0으로 채우면 틀린 점수가 난다.**

관련해서, 편한 대체 라벨도 거절했다. 비슷한 다른 지표로 결측을 채울 수 있었지만
그 지표 기준 성공인 후보의 8.8%가 실제로는 실패였다. 성공률이 부풀려진다.

---

## 13. 재현성의 전제를 실측한다

**교훈.** "시드만 바꿨을 때의 흔들림"을 잡음으로 쓰는 체계는 **학습이 결정적**이라는 전제 위에 선다.
그 전제를 확인하지 않으면 하드웨어 잡음이 측정 잡음에 섞인다.

**어떻게 드러났나.** GPU 히스토그램 집계는 같은 시드에서도 마지막 자리가 흔들린다.
그래서 XGBoost를 일부러 CPU로 학습했다. 행렬이 작아(368,000 × 7) GPU 이득도 없었고,
병목은 학습이 아니라 파일 읽기였다.

서로 다른 시점에 학습한 `model.json`이 **바이트 단위로 같은 것**을 확인해 전제를 실측으로 뒷받침했다.

---

## 14. in-sample 값을 성능 옆에 두지 않는다

**교훈.** 학습 데이터를 다시 예측한 값은 성능이 아니다. 표시 없이 홀드아웃 값 옆에 두면 오해를 부른다.

**어떻게 드러났나.** 최종 모델 보고서 첫 판에서 dev 열이 in-sample 값인데 표시가 없었다.
홀드아웃 값과 나란히 있어 "dev에서는 훨씬 좋다"로 읽혔다.

**무엇을 바꿨나.** 열 이름을 `dev_in_sample`로 바꾸고, out-of-fold 값과 둘의 차이(암기 격차)를 함께 실었다.

## 15. 한 번에 하나씩 바꾼다

**교훈.** 여러 개를 동시에 바꾸면 귀속이 안 된다. 학습이 분 단위면 **절제를 처음부터 계획에 넣는 것**이 가장 싸다.

**어떻게 드러났나.** 29번에서 목적함수·정규화·학습 대상 셋을 함께 바꿨다. 결과가 나아졌지만
무엇 때문인지 몰랐다. 절제를 따로 돌려서야 정규화가 어려운 층을 악화시킨다는 것이 드러났다.

## 16. 되돌리기 비싼 결정은 측정해서 정하되, 측정 비용이 본실행에 접근하면 그냥 실행한다

**어떻게 드러났나.** 외부 도구의 실행 모드를 표본으로 먼저 비교하려 했다(40분~2시간).
그런데 CPU 경로로 본실행 비용이 40시간대로 내려와 비교의 이득이 사라졌다.
게다가 그 도구는 feature 하나라서, 조합에서의 가치는 어차피 본실행 없이는 잴 수 없었다.
비교를 생략하고 바로 실행했다.

## 17. 버그처럼 보이는 것이 데이터의 성질일 때가 있다

**어떻게 드러났나.** 물·금속 범주 feature 6개가 거의 전부 상수였다. 추출기를 의심했다.
그런데 입력이 예측 구조라 **원래 물 분자와 독립 금속 이온이 없다.**
실험 구조를 전제로 설계한 feature는 예측 구조에서 성립하지 않는다.

**무엇을 바꿨나.** 버그가 아니므로 행렬에는 출처대로 남기고 선별 단계에서 제외했다.
feature를 지우면 왜 없는지가 기록에서 사라진다.
